# Maestro item 1861 — Allowlisted Admin Settings catalog

- Source: https://maestromojo.com/workspaces/#/board/11?item=1861
- Build started: 2026-08-11

Administrators need one obvious place to understand and safely change the runtime configuration that django-mojo intentionally supports from the database. Today configuration is fragmented across System Setup, Advanced, authentication configuration, generic settings APIs, and deployment files. Add a curated Settings area over the existing Setting system, showing effective provenance and routing owner-managed or file-only values without weakening their boundaries.

---

## Spec

**Kind:** feature · **Requested by:** Ian Starnes · **Source:** built-in Admin QA, 2026-08-11

### Acceptance Criteria

- The Admin sidebar has a first-class capability-gated Settings destination.
- A server-owned opt-in catalog declares stable key, section, description, type, constraints, default, resolver, raw/effective semantics, provenance, sensitivity, scope, writability, owner, and change behavior.
- Responses omit arbitrary Django settings, paths, environment names, secret material, raw ignored overrides, and raw exceptions.
- Initial catalog:
  - General: protected BASE_URL; immutable MOJO_INSTALLATION_UUID/SLUG.
  - Authentication: only the existing safe AUTH_CONFIG projection.
  - Users & sessions: global boolean overrides ALLOW_EMAIL_CHANGE, ALLOW_PHONE_CHANGE, ALLOW_USERNAME_CHANGE, ALLOW_SELF_DEACTIVATION.
  - Email/notifications: file-only or owner-managed sender/template posture, routed to Mailbox/EmailTemplate owners.
  - DNS/certificates: DNSMAN_ACME_CONTACT_EMAIL and DNSMAN_CERT_RENEW_DAYS are initially display/owner-only because existing-account and rescheduling semantics are not safe generic writes.
  - Edge/WebApps: protected EDGE_EXPECTED_TOPOLOGY and a global WEBAPP_BASE_URL override validated as a canonical public HTTPS origin; documented group rows remain supported.
  - Security/operations: monitoring topics, monitoring identity, secure redirect/cookie/HSTS posture, KMS configured state, and SYSTEM_SETUP_LOCAL_API_URL, all owner-managed or file-only.
- BASE_URL remains durable Setup-owned; identity immutable; monitoring AWS-owned; AUTH_CONFIG/topology keep their existing typed writer and literal-superuser authority.
- Catalog-owned overrides are global-only, typed, validated, non-secret, protected from alternate global writes, and use the existing Setting table—no new persistence model.
- Group-scoped rows remain compatible; global-only protection checks both original and target key/scope during create, update, rename, move, and delete.
- GET/POST catalog APIs reject key-backed mutations, require exact global authority and 600-second recent interactive auth, reread the active User, audit only actor/key/action/source, and never log bodies/values.
- Provenance follows each real resolver: dynamic Redis/DB/file, protected DB-only, static file-only, or computed/merged. AUTH_CONFIG distinguishes raw override from effective merged projection.
- Duplicate global rows are a fail-closed duplicate_override state. Set refuses ambiguity; Clear removes all locked global duplicates and invalidates Redis only after commit.
- Clear is idempotent and falls back visibly to deployment/default.
- manage_settings can enter the Admin source/bootstrap flow. Literal permissions.admin remains an exact grant, not a wildcard; only is_superuser is a wildcard.
- Settings publishes separate catalog-write, owner-display, and owner-edit capabilities. AUTH_CONFIG/topology controls are editable only with the old manage_advanced/admin plus active literal-superuser authority.
- The existing /api/account/admin/advanced/settings API remains supported; Advanced stops owning the duplicated form.
- The generic /api/settings remains for uncataloged and allowed group-scoped settings. Its legacy visibility of non-secret rows is documented; the catalog adds no confidential mutable values.
- Professional search/filter, typed inputs, dirty state, confirmation, skeleton/busy/440, success/error feedback, and wide/narrow layout are required.

## Plan

1. **Opt-in registry and truthful provenance.**
   - Add account/services/admin_settings.py with import-light immutable descriptors and private resolver/validator/writer callables.
   - Register core descriptors idempotently from AccountConfig.ready, DNS-owned descriptors from DnsmanConfig.ready, and Edge-owned descriptors from EdgeConfig.ready. Identical repeats succeed; conflicting definitions fail. Optional app absence omits that section safely.
   - Resolve actual source/effective semantics per descriptor. Bound non-secret values; return configured-only for sensitive static entries; report only ignored_database_override=true for ineffective file-only shadow rows.

2. **Scope-aware alternate-writer protection.**
   - Update account/models/setting.py so catalog-owned protection applies only to global rows and checks original plus target key/scope across create, save, rename, group/global move, and delete.
   - Preserve group inheritance, secret settings, uncataloged keys, validators, geofence invalidation, and existing system_settings protected behavior.
   - Avoid circular imports: registry metadata is import-light and model protection resolves it lazily.

3. **Dedicated global override writer.**
   - Reread an active literal User and exact current manage_settings/admin grant.
   - Validate catalog membership, override ownership, global scope, strict type, and key constraints. The four ALLOW values use booleans; WEBAPP_BASE_URL is a canonical public HTTPS origin.
   - Under the stable global lock, fetch every global row for the key. Set fails closed on duplicates; Clear deletes every locked duplicate. Publish hset/hdel only in transaction.on_commit. Never call the generic pre-commit cache-removal delete path.
   - Emit bounded post-commit audit metadata without values.

4. **Fail-closed REST and logging.**
   - Add account/rest/admin_settings.py and import it from rest/__init__.py.
   - GET /api/account/admin/settings returns schema-versioned catalog; POST accepts only set or clear shapes.
   - Add manage_settings to Admin source-session and bootstrap admission, publish catalog_write/owner_display/owner_edit capabilities, and gate mutations with denies_key_backed_session, requires_fresh_auth(600), and exact global permission.
   - Add the route to helpers/request.py sensitive-body classification and keep responses server-redacted.

5. **Keep real callers typed and owners intact.**
   - Make the four ALLOW_* consumers use kind=bool with their existing defaults so stored JSON false works.
   - AUTH_CONFIG/topology remain read-only unless the existing /advanced/settings authority and literal-superuser condition hold, and saves continue through that endpoint.
   - DNS contact/renewal are display/owner-only in this first catalog; no misleading generic save. File-only values remain get_static.
   - Document that generic /api/settings already exposes non-secret Setting rows to its legacy permission holders; do not claim catalog redaction changes that surface.

6. **First-class private feature.**
   - Add the settings feature provider and all four fixed rosters: server FEATURE_NAMES, private-asset FEATURES/feature manifest, JS descriptors/imports, and feature-local manifest.
   - Add settings capability to bootstrap and route #/settings.
   - Remove Settings route/form ownership from Advanced before registry insertion; update Platform’s hard-coded Advanced disclosure.
   - Build settings/feature.js, page.js, styles.css, manifest.json with section search/filter, badges, typed editors, dirty state, safe owner links, confirm Clear, shared loadingState/openBusy/finally, and global 440 flow.

7. **Preview, tests, and docs.**
   - Add deterministic Settings fixtures/provider and server dispatch for database/deployment/default, immutable/owner-only, sensitive configured-only, ignored override, duplicate, invalid, delay/error/440, set, and clear without logging values.
   - Add test_admin_settings plus update portal/platform/preview tests for exact catalog/rosters, permissions/admission, owner splits, strict types, group/global transitions, duplicate set/clear, cache rollback, audit/log redaction, boolean false consumers, optional apps, and compatibility APIs.
   - Add both developer-track Settings docs and indexes; update Admin/Platform/Advanced/settings-helper references for seven lanes, provenance, ownership, static boundaries, legacy generic visibility, and extension registration.

### UX Coherence Amendment

- **First-class navigation:** Settings is a sidebar item; Advanced is not. Recommended order: Dashboard, Web Apps, Domains & DNS, People, Activity, Platform, Settings. Exactly one item is active.
- **Progressive disclosure, not another giant form:** the default Settings view has a compact search and optional category chips. Each card shows friendly name, effective value/status, source badge, and one action. Open only one edit drawer/modal at a time; on narrow screens it becomes a bottom sheet. Exact key, raw/effective semantics, constraints, and provenance live under closed Technical details.
- **Categories:** General; Sign-in & registration; Users; Email; Domains & DNS; Edge & Web Apps; Security & operations.
- **Public API address:** label BASE_URL as Public API address, show current/missing state and Managed by System Setup, and Configure via a focused durable Setup link. Do not add a duplicate textbox or writer.
- **One UI home per control:** move Brand & auth pages, Login methods, Registration, and Expected fleet out of Advanced. Continue using their existing typed owner endpoint. Expected fleet uses token/chip inputs or explicit node/pool rows, never comma-separated text.
- **Row semantics:** database overrides offer Edit/Clear with explicit saved feedback; owner-managed rows show one real owner action; file-only rows show Deployment setting and concise Change KEY in Django production settings and deploy; sensitive values show only configured state; immutable identity has no action; duplicate overrides disable Set and offer one confirmable Clear conflicting database overrides.
- **No fictional destinations:** SES sender/templates route to the owning Setup section, not nonexistent Mailbox/EmailTemplate pages. Certificates remain automatic/expert detail, not a primary operator journey.
- **Connect without competing:** when installation setup is incomplete, Settings shows one top callout Continue Setup. Settings never becomes a second setup wizard.
- **Remove the misleading screenshot UI:** remove protected settings from Platform/Advanced copy, remove the duplicated Advanced typed form, and remove Platform’s expanded Advanced route directory. Keep the legacy typed API only as backend authority.
- **Wide and 390px acceptance:** no horizontal overflow; long origins/keys wrap; category controls wrap/scroll; modal becomes bottom sheet; skeleton, dirty, invalid, saving, saved, error, duplicate, clear, and 440 states are visible and keyboard-safe; raw data and keys remain collapsed by default.
